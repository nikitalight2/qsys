# Rebuilding grandMA2 Shows as Recipe-Driven grandMA3 Shows

grandMA3 cannot open a grandMA2 show, and the only official bridge, the **"Save as grandMA3" button in grandMA2 onPC 3.9 / Mode2**, produces a show whose patch, groups, value presets, sequences and executors come across but whose macros, embedded/global/universal presets, non-trivial effects and remotes do not ([grandMA2 manual: Show File Converter](https://help.malighting.com/grandMA2/en/help/key_backup_menu_save_as_grandma3.html)). Both native show files are undocumented binaries, so a third-party converter must read grandMA2's `Export` XML (root `<MA>`, namespace `schemas.malighting.de/grandma2`) and write grandMA3's per-object library XML (root `<GMA3 DataVersion="…">`) plus command macros that grandMA3 onPC imports and executes. The two data models are close enough at the cue/preset level for a mechanical translation (same nine feature groups, same preset modes, same five cue triggers, preset references in cues), but they diverge where grandMA3 is genuinely new: a 3-D selection grid instead of linear selection, Phasers instead of Effect pool objects, executor rows 101/201/301 instead of fader/button pages, tree-path addressing in the command line, and Recipes. Recipes are the key to the second goal: a recipe line is a reference (group + preset + MAtricks + timing spread) that the console "cooks" into cue data, so a show built from groups and Global presets can be re-rigged by editing groups and running `Cook Sequence N` ([grandMA3 2.5 QSG Recipes](https://help.malighting.com/grandMA3/2.5/HTML/qsg_recipes.html)). The catch that shapes the entire converter design is that **standard recipe lines cannot hold raw values**; every value that should survive a rig change must first be turned into a preset, and per-fixture one-offs (selective positions, hand-tweaked levels) stay as hard values that outrank recipe output until re-cooked ([grandMA3 2.2 Recipes](https://help.malighting.com/grandMA3/2.2/HTML/recipes.html)). The build plan in the second half of this report therefore runs through a "palette extraction" stage that mines presets out of grandMA2 cue data, emits groups, Global presets and recipe lines, and keeps a parallel hard-value cue part for everything that cannot be expressed as group × preset. Several load-bearing details (the exact XML of a grandMA3 recipe line, the real `DataVersion` string of 2.5.x, and a complete attribute-name cross-reference) are not published anywhere and must be harvested from the two free onPC applications before code is written.

# Part A — Research findings

## The two consoles share a cue skeleton but differ in selection, effects and addressing

At the level a converter cares about most, cues and presets, the systems are congruent. Both organise attributes into the same **nine top-level categories** in the same order: grandMA2 calls them Preset Types 1–9 (Dimmer, Position, Gobo, Color, Beam, Focus, Control, Shapers, Video) and grandMA3 calls them Feature Groups (Dimmer … Shaper, Video), each with its own preset pool ([grandMA2 QSG Preset Pool](https://help.malighting.com/grandMA2/en/help/grandma2_quick_start_guide/key_12_preset_pool.html); [grandMA3 2.5 Presets](https://help.malighting.com/grandMA3/2.5/HTML/presets.html)). Both store cue values as **references to presets** rather than copies, so updating a preset updates every cue that uses it ([grandMA3 2.4 Presets Use](https://help.malighting.com/grandMA3/2.4/HTML/presets_use.html)). Both have Selective, Global and Universal preset modes with identical meanings, though grandMA3 lets one preset carry several modes at once and gives each pool a default mode ([grandMA3 2.5 Presets](https://help.malighting.com/grandMA3/2.5/HTML/presets.html)). grandMA3 adds **five unfiltered "All" pools for 14 default pools**, and MA's own converter drops grandMA2 effects into "preset pool 22", which shows that pool numbering extends well beyond 14 ([grandMA3 1.0 Preset Pools](https://help2.malighting.com/Page/grandMA3/presets_pools/en/1.0); [grandMA2 3.9 Release Notes](https://help.malighting.com/grandMA2/en/help/release_notes/key_releasenotes.html)).

The cue model is equally close. Both have cue numbers with up to three decimals (grandMA2 0.001–9999.999), cue parts, per-cue fade/delay with per-attribute override, and the same **five trigger types: Go, Time, Follow, Sound, BPM** ([grandMA2 Cue keyword](https://help.malighting.com/grandMA2/en/help/key_keyword_cue.html); [grandMA3 2.0 Sequence Sheet](https://help.malighting.com/grandMA3/2.0/HTML/cue_sequence_sheet.html)). grandMA3 allows **256 parts per cue** and an "Allow Duplicates" flag that lets one attribute appear in several parts ([grandMA3 2.3 Cue Store](https://help.malighting.com/grandMA3/2.3/HTML/cue_store.html)). Where grandMA2 folds Assert, X-Assert, Release, Break and X-Break into a single cue "Mode" column, grandMA3 splits them into separate Assert, X-Assert and Release columns plus a Tracking Distance column; MA2's "Release" (turn off the executor when the fade completes) and MA3's "Release" (release tracked values from this cue forward) are not the same thing, and no MA3 counterpart to Break/X-Break was found (inferred from the two cue-mode pages: [grandMA2 Cue Modes](https://help.malighting.com/grandMA2/en/help/key_adv_seq_cue_modes.html); [grandMA3 2.4 Cue Tracking](https://help.malighting.com/grandMA3/2.4/HTML/cue_tracking.html)). MIB maps Early→Early and Late→Late, and a grandMA2 MIB-from-cue becomes MA3's "MIB Mode = Defined" with a MIB Target; UponGo, Force modes and MIB Preference exist only on MA3 ([grandMA3 2.4 Cue MIB](https://help.malighting.com/grandMA3/2.4/HTML/cue_mib.html)).

The divergences are structural rather than cosmetic. **Patch identity**: grandMA2 has two parallel ID spaces (Fixture ID and Channel ID); grandMA3 has a primary FID plus optional CID drawn from eight ID types, with subfixtures addressed as `parent.sub` and `17.` selecting a parent with all its cells ([grandMA3 2.5 QSG First Patch](https://help.malighting.com/grandMA3/2.5/HTML/qsg_first_patch.html); [grandMA3 2.1 Fixture Sheet](https://help.malighting.com/grandMA3/2.1/HTML/operate_fixture_sheet.html)). Fixture types in grandMA3 are GDTF-structured (Activation/Feature/Deactivation groups, physical units such as Angle for gobo index), which is why converted grandMA2 types are reported to lose XYZ and pan/tilt behaviour ([grandMA3 2.1 Attribute Definitions](https://help.malighting.com/grandMA3/2.1/HTML/patch_attribute_definitions.html); [MA forum: switch from gMA2 to gMA3](https://forum.malighting.com/forum/thread/69773-switch-from-gma2-to-gma3-which-way/)). **Selection**: grandMA2 selections are strictly linear and MAtricks works with Interleave/Block/Wings on that line; grandMA3 stores every selection in a **3-D grid (X/Y/Z)** with MAtricks Blocks, Groups, Wings, Width and Shuffle per axis, and a linear MA2 group becomes an MA3 group occupying X only ([grandMA3 2.2 Selection Grid](https://help.malighting.com/grandMA3/2.2/HTML/operate_selection.html); [MA forum: Selection](https://forum.malighting.com/forum/thread/69177-selection/)). **Effects**: grandMA2 effects are pool objects with lines (attribute, form, rate, size, phase, width, groups/blocks/wings) applied to a selection; grandMA3 Phasers are per-attribute multi-step value sequences living inside presets or cues, with per-step Width/Transition/Accel/Decel and a Speed, Phase and Measure layer ([grandMA2 Predefined Effects](https://help.malighting.com/grandMA2/en/help/key_effects_predefined.html); [grandMA3 2.5 Phaser](https://help.malighting.com/grandMA3/2.5/HTML/phaser.html)). ACT's guidance is that "any standard grandMA2 Form can be replicated with two or more grandMA3 Phaser Steps using the right combination of Width, Transition, Acceleration, and Deceleration" ([ACT KB 25504931](https://support.actentertainment.com/knowledgeBase/25504931); source not fully verified; confirm against the official manual). **Executors**: grandMA2 numbers fader executors 1–90 and button executors 101–190 on separate fader and button pages; grandMA3 numbers by physical row, **101–190 (button), 201–290 (button+fader), 301–390 (button+knob)**, on a single page type with up to 9,999 pages per data pool, and MA's converter maps 1–90 → 201–290 and 101–190 → 101–190 ([grandMA2 Exec on screen](https://help.malighting.com/grandMA2/en/help/key_exec_on_screen.html); [grandMA3 2.5 QSG Cue Executor](https://help.malighting.com/grandMA3/2.5/HTML/qsg_cue_executor.html); [grandMA2 3.9 Release Notes](https://help.malighting.com/grandMA2/en/help/release_notes/key_releasenotes.html)). **Command syntax**: the selection/value grammar is similar, but grandMA3 sets object properties with `Set <Object> Property "<Name>" "<Value>"`, addresses objects as a tree (DataPool / Page / Executor, Sequence / Cue / Part), and MA Lighting states flatly that macro commands "cannot be translated to the grandMA3 syntax" and must be verified by hand ([grandMA3 2.2 Set keyword](https://help.malighting.com/grandMA3/2.2/HTML/keyword_set.html); [grandMA2 3.9 Release Notes](https://help.malighting.com/grandMA2/en/help/release_notes/key_releasenotes.html)).

## Both show files are opaque; XML export and import are the only working interfaces

Nothing documents the inside of either native show file. The grandMA2 `.show.gz` is a gzip-wrapped binary stream that begins with the bytes `MA DATA`, with a little-endian version field at bytes 8–11; the only public tool touching it is a show-downgrader that rewrites that field ([Niasus17/grandMA2-show-downgrade](https://github.com/Niasus17/grandMA2-show-downgrade)). The grandMA3 `.show` starts with the ASCII bytes `GMA3` and is refused by third-party readers as "a proprietary, undocumented format" ([PhotonBoard: grandMA3 show file](https://github.com/Achorius/PhotonBoard/blob/main/docs/format/grandma3-show-file.md)). grandMA2's own manual states that "it is not possible to export or import the show, or a part of the show to any other console format" ([grandMA2 manual: Export and Import](https://help.malighting.com/grandMA2/en/help/key_export_and_import.html)). Every integration found, MLA, FocusTrack, CuePoints, ETC's MA-to-Eos service and all community Lua tools, works from XML exports. **No XSD for either format was located**, although grandMA2 offers an `Export … /schema` option that writes MA.xsd from the console itself ([grandMA2 manual: Export keyword](https://help.malighting.com/grandMA2/en/help/key_keyword_export.html)).

**grandMA2 export XML.** Every file is UTF-8 (often with BOM), root `<MA xmlns="http://schemas.malighting.de/grandma2/xml/MA" major_vers="3" minor_vers="9" stream_vers="60">`, an `<Info datetime showfile/>` element, then object elements. Observed console exports include `<Layer index name>` (patch, with `<Fixture fixture_id|channel_id>`, `<FixtureType name><No>`, `<AbsolutePosition>`, one `<SubFixture>` per instance carrying `<Patch><Address>` as an absolute DMX address), `<FixtureType index name mode>` (with `Modules/Module/ChannelType/ChannelFunction/ChannelSet` and `Instances`), `<Group index name>` (with `<Subfixtures><Subfixture fix_id sub_index/>`), `<Preset index name preset_mode SpecialUse>`, `<Sequ index name timecode_slot forced_position_mode>`, `<Macro index name><Macroline index><text>`, and `<Timecode>` ([stooEe/Ma2-Sandbox](https://github.com/stooEe/Ma2-Sandbox); [bozi6/hello-world testshow.xml](https://github.com/bozi6/hello-world/blob/master/ma2xml2capture/xmlz/testshow.xml); [cbdevnet/xlaser fixture type](https://github.com/cbdevnet/xlaser/blob/master/console-support/kitinfo@xlaser@opengl.xml); [aGuyNamedJonas/grandma2-snippets](https://github.com/aGuyNamedJonas/grandma2-snippets)). Layouts are exported as a `<Group>` that contains `<LayoutData>` ([stooEe layout.xml](https://github.com/stooEe/Ma2-Sandbox/blob/main/data/layout.xml)). The crucial join key is the **library attribute name**: preset exports list `<PresetValue Value="60"><Channel fixture_id="1" attribute_name="TILT"/>` and sequence exports list `<CueData><Channel fixture_id="201" attribute_name="DIM"/><Value>…</Value>`, using the same strings (`DIM`, `PAN`, `TILT`, `COLORRGB1..3`, `GOBO1`, `SHUTTER`, `ZOOM`, `FOCUS`, `CTO`, `BLADE1A`, `MSPEED`) that appear in `ChannelType@attribute` inside fixture-type files ([stooEe preset_0.1.xml](https://github.com/stooEe/Ma2-Sandbox/blob/main/data/preset_0.1.xml); [AuraLuxMuse read_sequence_cue.py](https://github.com/joeyjoestar111/AuraLuxMuse/blob/main/utils/read_sequence_cue.py)). Values appear on a 0–100 percent-like scale (dimmer 0–100, pan −270…270 physical), multi-cell fixtures carry `subfixture_id`, and a cue value can be the keyword `Release`. Preset scope is encoded by container: `<Values><Channels>` for selective per-fixture data, `<ChannelTypes><ChannelType fixture_type module attribute>` for per-type (global) data, `<Attributes><Attribute name>` for universal data, and a `<Fades>` block instead of `<Values>` for timing-only presets ([grandma2-snippets dimmer-fade-presets.xml](https://github.com/aGuyNamedJonas/grandma2-snippets/blob/master/single-cue-magic/dimmer-fade-presets.xml); the mapping of container to mode is inferred). Sequence cue numbers use `<Number number sub_number>` with `sub_number` in thousandths, a `<MibCue>` child records the MIB source, `<CueData value_multipart_index effect_multipart_index>` ties a value to a part, and `<CuePart index name basic_fade basic_outfade>` holds part timing ([only-cue MA2SequenceXMLGenerator](https://github.com/chienchuanw/only-cue/blob/main/OnlyCue/MA2/MA2SequenceXMLGenerator.swift)). **No reachable console export showed a cue with preset references, per-attribute fades or effect references**, so those attribute names remain a gap. Exports are driven by `Export [Object-list] ["filename"] /nc /o /path=…`; omitting the filename yields one file per object, and MLA's bulk macro uses lines such as `Export Preset 0.1 thru 0.999 "mla_presets_all"` per pool ([grandMA2 manual: Export keyword](https://help.malighting.com/grandMA2/en/help/key_keyword_export.html); [MLA: Exporting grandMA2 data](https://www.manula.com/manuals/avld/mla/14/en/topic/exporting-grandma-2-data)). Files land in `C:\ProgramData\MA Lighting Technologies\grandMA\gma2_V_x.x\importexport` on onPC ([grandMA2 manual: Export and Import](https://help.malighting.com/grandMA2/en/help/key_export_and_import.html)).

**grandMA3 library XML.** All files share `<?xml version="1.0" encoding="UTF-8"?><GMA3 DataVersion="a.b.c.d">` with the object class as child. A sequence serialises as `<Sequence Name Guid Tracking="Yes" …><Cue Name="OffCue"/><Cue Name="CueZero" No="  0"/><Cue Name="…" No="  1" TrigType="Follow" TrigTime="4"><Part Part="0" CueInFade="3.000" CueOutFade="5.000" CueInDelay="0.500" Preset2Fade="6.000"><Phaser IDType="0" ID="101" Attribute="Dimmer" [AbsPreset="4.1"] [Fade="8"]><Step Function="Dimmer" Absolute="100"/></Phaser>…` where **every value, even a static one, is a one-step Phaser** and `IDType` 0 = FID, 1 = CID, 2 = universal fixture ([PhotonBoard sequence.xml](https://github.com/Achorius/PhotonBoard/blob/main/test-fixtures/interchange/ma3/sequence.xml); [PhotonBoard ma3.ts](https://github.com/Achorius/PhotonBoard/blob/main/src/main/interchange/ma/ma3.ts)). A generator validated against a real 2.4.2.2 console notes that the cue `No` is right-justified to three characters, the file begins with a UTF-8 BOM, and the full Sequence attribute set (`AutoStart`, `AutoStop`, `SoftLTP`, `SequMIB`, `WrapAround`, `MasterGoMode`, `Tracking`, `RateScale`…) should be mirrored verbatim: "Do not 'clean' them" ([reacue lighting.py](https://github.com/herve8940/reacue/blob/main/reacue_mcp/lighting.py)). Presets are `<Preset Name No="4.1" PresetModeInternal="Selective|Universal"><PresetData Size="n"><Phaser IDType ID Attribute><Step Function Absolute/>`; groups are `<Group Name Guid><SelectionData Size="n"><Item IDType="0" ID="101" X="0" Y="0" Z="0"/>`; macros are `<Macro Name Guid><MacroLine Command="…" Wait="0.10"/>` and a 1.4.0.2 macro file is structurally identical to 2.x output ([PhotonBoard presets-group.xml](https://github.com/Achorius/PhotonBoard/blob/main/test-fixtures/interchange/ma3/presets-group.xml); [PhotonBoard macro-vivaldi.xml](https://github.com/Achorius/PhotonBoard/blob/main/test-fixtures/interchange/ma3/macro-vivaldi.xml)). Timecode shows nest `TrackGroup / Track(Target="ShowData.DataPools.Default.Sequences.Song") / TimeRange / CmdSubTrack / CmdEvent(CueDestination)`, and references are **textual object paths**, which is also how users repair broken datapool imports by hand ([reacue lighting.py](https://github.com/herve8940/reacue/blob/main/reacue_mcp/lighting.py); [MA forum 68636](https://forum.malighting.com/forum/thread/68636-datapool-import-export-workflow-lost-references/)). GUIDs are 16 space-separated hex bytes. Import is lenient about age: a macro with `DataVersion="2.3.0.0"` imported and ran on onPC 2.5.1.0, and files at 1.4.0.2 and 1.9.7.0 still import, but **the exact DataVersion a 2.5.1.x console writes was not found in any public sample**, and show files from a future version are refused, so a newer-than-target DataVersion is a risk ([kjoreplan-ma3 ma-versions.json](https://github.com/jorgen-iden/kjoreplan-ma3/blob/main/src/lib/config/ma-versions.json); [Naostage autozoom PR #2](https://github.com/Naostage/grandma3-autozoom-plugin/pull/2); [grandMA3 2.0 Release Notes](https://help.malighting.com/grandMA3/2.0/HTML/key_releasenotes.html)). Files are read from `MALightingTechnology/gma3_library/datapools/{sequences,presets,macros,timecodes,plugins}/`, `gma3_library/patch`, `gma3_library/fixturetypes` and `gma3_library/mvr` ([grandMA3 2.0 Folder Structure](https://help.malighting.com/grandMA3/2.0/HTML/fm_folder_structure.html); [Reaper_Markers_GrandMA3](https://github.com/edendolev1/Reaper_Markers_GrandMA3)). **No public sample of Layout, Appearance, Page/Executor, World, Filter, MAtricks or Recipe-line XML exists**; those element names are unknown.

**Import routes into grandMA3.** Four routes exist and can be mixed. The `Import [Object] Library "file.xml" [At <Object> N]` keyword (shortcut `Im` since 2.3) loads a library file into the first free pool slot or a named one, e.g. `Import Macro Library "color.xml" At Macro 42`, `Import Sequence Y "NAME.xml"` ([grandMA3 2.5 Import keyword](https://help.malighting.com/grandMA3/2.5/HTML/keyword_import.html); [MLA: Importing into grandMA3](https://www.manula.com/manuals/avld/mla/14/en/topic/importing-sequence-and-timecode-files-into-the-grandma3)). The Show Creator menu (2.x; "Import/Export" in 1.9) does the same graphically with "Include Dependencies" ([grandMA3 2.5 Import/Export](https://help.malighting.com/grandMA3/2.5/HTML/import-export.html)). A macro can chain `Drive 2`, `Import …`, `Patch Fixture N U.AAA`, `Store`, `Label`, `Assign Sequence S At Page P.E`, which is exactly what the real `macro-vivaldi.xml` does. Lua plugins can call `Cmd("…")` for any command string, `Import(handle, …)` to merge XML without a pop-up, and `AddFixtures({mode=…, amount=…, fid=…, patch="U.AAA"})` to create fixtures programmatically after moving the destination into the patch ([grandMA3 2.1 Cmd](https://help.malighting.com/grandMA3/2.1/HTML/lua_objectfree_cmd.html); [grandMA3 2.1 AddFixtures](https://help.malighting.com/grandMA3/2.1/HTML/lua_objectfree_addfixtures.html); [gma3-mcp patch.md](https://github.com/bdstark/gma3-mcp/blob/main/docs/tools/patch.md)). The Lua core changed to 5.5.0 in 2.5 and hard-coded datapool child indices broke, so property names, not indices, must be used ([Naostage autozoom PR #2](https://github.com/Naostage/grandma3-autozoom-plugin/pull/2)). **No command-line keyword adds a fixture of a given type with a FID**; that is a Patch-menu, MVR, patch-XML or Lua `AddFixtures` operation ([grandMA3 2.5 Add Fixtures](https://help.malighting.com/grandMA3/2.5/HTML/patch_add_fixtures.html)).

## MA's own converter covers the easy 60 percent and defines the gaps worth filling

The official converter has matured from a patch-only exporter in 2021 (gMA2 3.9.60.4 / gMA3 1.4.2.1: "only patch converts") to a tool that by 3.9.60.89 converted patch, fixture types, worlds, filters, groups, value-layer presets with timings, sequences and cue timings, executors and pages, special masters, appearances and infos-as-notes ([MA forum 4039](https://forum.malighting.com/forum/thread/4039-grandma2-fixture-type-import/); [grandMA2 3.9 Release Notes](https://help.malighting.com/grandMA2/en/help/release_notes/key_releasenotes.html); [grandMA2 manual: Show File Converter](https://help.malighting.com/grandMA2/en/help/key_backup_menu_save_as_grandma3.html)). Two of its behaviours are worth copying: **chaser-only sequences receive a Trigger Time of BPM/60 per cue**, and effects are placed in **preset pool 22, renamed "Effects"**, with simple forms expressed as acceleration/deceleration values and Stomp rewritten as a hard 0 with a single relative step ([grandMA2 3.9 Release Notes](https://help.malighting.com/grandMA2/en/help/release_notes/key_releasenotes.html)). Its documented limitations are the specification for a third-party tool: macro commands are not translated; only "simple predefined forms" of effects convert; effect data inside presets, timing-only presets, embedded presets, and global/universal presets are "not converted, yet"; effect lines on attributes outside the preset type are dropped; X-keys 5/6/15/16 are dropped; remote type/target is lost; executors without sequences or selective effects are skipped; fixture types with more than 8,192 channel sets are truncated; and it does not run under Parallels ([grandMA2 manual: Show File Converter](https://help.malighting.com/grandMA2/en/help/key_backup_menu_save_as_grandma3.html); [grandMA2 manual: Limitations 3.9](https://help2.malighting.com/Page/grandMA2/limitations/en/3.9)). Converted fixture types carry Source = "grandMA2", **cannot be exported as GDTF** and are excluded from MVR export ([grandMA3 2.0 Export Fixture Types](https://help.malighting.com/grandMA3/2.0/HTML/ft_export.html)). Users in 2026 still call results "unsatisfactory", report that "all P/T fixture types lost proper XYZ behavior", and seriously propose recording grandMA2's DMX output into a grandMA3 as an alternative ([MA forum 69773](https://forum.malighting.com/forum/thread/69773-switch-from-gma2-to-gma3-which-way/)). The most repeated advice is **version pairing**: convert with the grandMA2 3.9.6x build that matches the target grandMA3 version, and expect converted files older than 1.9 to need a two-hop upgrade because 2.x refuses shows saved before 1.9 ([MA forum 7931](https://forum.malighting.com/forum/thread/7931-convert-show-from-ma2-to-ma3/); [grandMA3 2.0 Load a Show File](https://help.malighting.com/grandMA3/2.0/HTML/sfh_load.html)).

Third-party prior art is fragmentary and none of it is end-to-end. A free Python **MA2-to-MA3 macro converter** (fiets.de, c. 2020) rewrites macro XML but predates later syntax changes ([fiets.de Downloads](https://fiets.de/downloads/)). **GMA Toolbox** (freeware, closed source) has a bidirectional Preset Mode2/3 Converter that works on XML and, since version 36.3, maps attribute names between Mode2 and Mode3, plus a Patch Creator that emits grandMA2/grandMA3 patch, position and group macros from MVR ([GMA Toolbox Preset Mode Converter](https://www.gmatoolbox.app/tools/preset-mode-converter/); [GMA Toolbox Changelog](https://www.gmatoolbox.app/changelog/); source not fully verified; confirm against the official manual). ma.tools sells a Lua **PatchImporter** (CSV/MVR into MA3 patch, requires 2.5.0.0+) and Ctrl+Cee sells an **MA3-Patch-to-MA2** plugin for 9.99 EUR ([ma.tools PatchImporter](https://ma.tools/plugins/patchimporter); [AddOnDesk](https://addondesk.com/product/ma3-patch-to-ma2/)). The open-source **gma3-mcp** project (MIT) is the most directly reusable blueprint: its Lua bridge plus command generator writes recipe cues with `Assign`/`Set`/`Cook` strings and has a live probe record against onPC 2.5.1.0 ([gma3-mcp recipes.md](https://github.com/bdstark/gma3-mcp/blob/main/docs/tools/recipes.md)). For fixture types, the MIT libraries `pymvr`/`pygdtf` read and write MVR 1.6 and GDTF ([open-stage/python-mvr](https://github.com/open-stage/python-mvr)), but **no tool converts grandMA2 fixture XML to GDTF**, and GDTF Share's forum answer is "not aware of such tool" ([GDTF Share forum 1003](https://gdtf-share.com/forum/index.php?%2Ftopic%2F1003-create-gdtf-fixture-from-ma2-and-cad%2F=)). The practical consequence, confirmed by the community pattern, is that a new converter should **re-map MA2 fixture type + mode names to native grandMA3 library or GDTF Share types** instead of carrying MA2 profiles, and treat MVR as a patch-and-position side channel only, since MVR imports leave "dummy" fixtures when GDTFs are missing ([MA forum 7861](https://forum.malighting.com/forum/thread/7861-import-xml-patch/); [Depence: export MVR to grandMA3](https://help.depence.com/depence-tips-and-tricks/how-to-export-mvr-to-grandma3)).

## Recipes make cues rig-independent, but only through groups and presets

A recipe "contains one or multiple recipe lines describing what should happen based on a set of information", and cooking writes the result as values into a cue part, preset or programmer part ([grandMA3 2.5 Recipes](https://help.malighting.com/grandMA3/2.5/HTML/recipes.html)). Introduced in 1.4 with the ingredients "fixture selection (groups), values (presets), MAtricks, fade, delay, speed, and phase" ([grandMA3 Release Notes 1.4](https://help.malighting.com/grandMA3/2.4/HTML/key_rn_v1_4.html)), a line today carries a Selection (group, or `<From Value>` to take the preset's own fixtures), Values (a preset), a MAtricks reference and/or inline X/Y/Z MAtricks columns (XWings, XBlock, XGroup, XWidth, XShift, XShuffle…), a Filter, Fade/Delay/Speed/Phase From/To pairs per axis, an Enabled flag, a Selection Mode (Normal passes values to subfixtures; Strict applies only to listed fixtures) and, since 2.4, an Attributes filter ([grandMA3 2.4 Recipe Editor](https://help.malighting.com/grandMA3/2.4/HTML/recipe-sheet.html); [gma3-mcp probe 2.5.1](https://raw.githubusercontent.com/bdstark/gma3-mcp/main/docs/probes/sb-05-recipes-macos-2.5.1.md)). Recipes attach to **cue parts, not cues** (default part 0), and to presets ([MA forum 8242](https://forum.malighting.com/forum/thread/8242-syntax-for-assigning-matricks-pool-item-to-recipe-line-in-sequence/)). The design constraint that drives everything downstream: **"you cannot type raw values into a recipe line; values must live in a preset first"**, and if the preset is empty the recipe cooks into the programmer instead ([grandMA3 2.2 Recipes](https://help.malighting.com/grandMA3/2.2/HTML/recipes.html)). Version 2.4 added Phaser Recipes (lines with two or more steps) whose steps accept `Value Absolute` (e.g. dimmer 50 %) and `Value Relative` (e.g. −20 %), Shapes, Adaptive Measure and Adaptive Width ([grandMA3 2.4 Features](https://help.malighting.com/grandMA3/2.4/HTML/rn_features-2-4.html)); whether a single-step standard line can take an absolute value was not confirmed.

Cooking has four modes. `Cook [Object] /Merge` removes previously cooked values, cooks fresh and replaces them at the destination; `/MergeLowPriority` replaces cooked data but never touches non-cooked (hard) data; `/Overwrite` deletes everything in the target first ("a very dangerous function"); `/Remove` deletes cooked data ([grandMA3 2.2 Cook keyword](https://help.malighting.com/grandMA3/2.2/HTML/keyword_cook.html); [grandMA3 2.3 Cue Recipes](https://help.malighting.com/grandMA3/2.3/HTML/cue_recipe.html)). A live matrix on onPC 2.5.1 confirms it: `/MergeLowPriority` keeps hard values everywhere, `/Merge` replaces the hard value only on the recipe's own fixture+attribute, `/Overwrite` leaves only cooked data, and a shrinking group drops the cooked data of removed fixtures ([gma3-mcp probe](https://raw.githubusercontent.com/bdstark/gma3-mcp/main/docs/probes/sb-05-recipes-macos-2.5.1.md)). Editing or assigning a line auto-cooks with MergeLowPriority; deleting a line does not auto-cook; MA staff state that "by default, auto-cooking doesn't touch values that have been manually stored to the Cue" ([grandMA3 2.5 Recipes](https://help.malighting.com/grandMA3/2.5/HTML/recipes.html); [MA forum 68353](https://forum.malighting.com/forum/thread/68353-when-to-cook-manually/)). **Hard values always outrank recipe values**: "Values in a cue part outrank the cue part's recipe value, and preset values outrank preset recipe values" ([grandMA3 2.2 Recipes](https://help.malighting.com/grandMA3/2.2/HTML/recipes.html)). Cooked values are flagged (green marker in the Track Sheet; `mask_cooked` 511 via Lua) and otherwise behave as ordinary tracked cue data, so tracking, release and fades operate on cooked values at playback time, not on the recipe (documented flag, inferred consequence; [MA forum 68814](https://forum.malighting.com/forum/thread/68814-recipe-vs-stored-data-in-sequence-indication-management/)). On 2.5.1 a change to a referenced group or preset was observed to re-cook in the background after roughly three seconds, matching 2.5's statement that "changing the ingredients leads to a re-cooking" ([grandMA3 2.5 Release Notes](https://help.malighting.com/grandMA3/2.5/HTML/release-notes-2-5.html); [gma3-mcp probe](https://raw.githubusercontent.com/bdstark/gma3-mcp/main/docs/probes/sb-05-recipes-macos-2.5.1.md)); older advice was to cook manually, and `/Overwrite` when fixtures were removed ([MA forum 9186](https://forum.malighting.com/forum/thread/9186-phaser-preset-reference-broken-when-changing-selection-in-recipe/)).

Which preset mode to feed a recipe matters for re-rigging. The manual's own guidance: "If the fixture type changes, the global preset needs to be updated. The selective preset links to the global preset values and does not need to be updated. The universal fixture is unaffected by the fixture change" ([grandMA3 2.2 Presets](https://help.malighting.com/grandMA3/2.2/HTML/presets.html)). A recipe line's cooked coverage follows each fixture's own selective row, else the global row of its type, else a universal row ([gma3-mcp recipes.md](https://github.com/bdstark/gma3-mcp/blob/main/docs/tools/recipes.md)), so a **Global preset per fixture type is the natural "look" carrier**, Universal works for type-agnostic attributes such as dimmer, and Selective presets only cover the fixtures that were present when they were stored. Universal presets in recipes have known holes: slotted attributes such as colour wheel C1 need a placeholder on the universal fixture, and adding a selection to a recipe turned clean universal presets into universal+selective ([MA forum 69308](https://forum.malighting.com/forum/thread/69308-universal-fixture-missing-c1/); [MA forum 69925](https://forum.malighting.com/forum/thread/69925-universal-recipe-phaser-presets-without-selective/)). Distributions depend on the **selection grid, not the fixture count**: a user had to recalculate phases when going to three fixtures, and 1.7/2.0/2.4 added phase-range recalculation, range-relative MAtricks and Adaptive Measure/Width to mitigate it ([MA forum 7661](https://forum.malighting.com/forum/thread/7661-width-and-phases-in-recipes/); [grandMA3 2.0 Release Notes](https://help.malighting.com/grandMA3/2.0/HTML/key_releasenotes.html)). There is **no built-in cue-to-recipe conversion** ("desired by many, but does not yet exist"), and copying cues with status or using Block creates hard values ([MA forum 68425](https://forum.malighting.com/forum/thread/68425-transform-cue-to-recipe/); [MA forum 8922](https://forum.malighting.com/forum/thread/8922-cue-hard-values-to-cue-recipe/)).

The creation syntax is simple and verified. `Assign Group 908 At Sequence 9060 Cue 1 Part 0.1` creates recipe line 1 on part 0 with that selection; `Assign Preset 4.4 At … Part 0.1` sets the values; `Assign MAtricks 12 At … Part 0.1` adds the MAtricks reference; assigning to a non-existent line index appends without gaps; `Set Sequence a Cue b Part c.d Property "XWings" 2` (or `"Enabled" "No"`, `"SelectionMode" "Strict"`, `"FadeFromX"`…) sets columns; `Delete … Part 0.2 /NoConfirmation` removes a line; the same pattern works on presets as `Assign Group 1 At Preset 23.921.1` ([gma3-mcp probe](https://raw.githubusercontent.com/bdstark/gma3-mcp/main/docs/probes/sb-05-recipes-macos-2.5.1.md); [ACT KB: Recipe syntax](https://support.actentertainment.com/knowledgeBase/34108761), source not fully verified; confirm against the official manual). In Lua the `Selection` property expects a group handle, not a name string, and creating lines with `part:Insert()` is reported broken since 2.4, so the robust path is `Cmd()` with the Assign/Set strings followed by `Cook Sequence N /MergeLowPriority` ([MA forum 68826](https://forum.malighting.com/forum/thread/68826-assign-selection-recipe-line-lua/); [MA forum 69760](https://forum.malighting.com/forum/thread/69760-calling-nil-value-when-creating-sequence-through-lua/)). **The XML serialisation of a recipe line was not found in any public source**; it is presumably `<StandardRecipe …/>` / `<PhaserRecipe …/>` children of `<Part>` with references as object paths, but this is inferred and must be confirmed by exporting a sample sequence.

# Part B — Instructions: building the MA2 → MA3 converter

This half turns the findings into a build plan. Statements are tagged **[documented]** when they rest on an official page or a verified file, **[community]** when they rest on forum or third-party reports, and **[inferred]** when they are design decisions or reasoning. Lists are used deliberately here because the reader will execute them.

## B1. Recommended architecture

The converter is a pipeline with a strict intermediate model in the middle, so that the grandMA2 reader and the grandMA3 writers can be tested and versioned independently.

```
grandMA2 onPC 3.9.x                     Converter (offline)                        grandMA3 onPC 2.5.x
───────────────────           ───────────────────────────────────────           ───────────────────────────
Export macro ──► XML files ──► [1] MA2 XML reader ──► [2] Intermediate   ──► [4] MA3 writers ──► gma3_library/…
(Layer, FixtureType,            (namespace-agnostic,     Show Model (IR)        ├─ patch XML / GDTF         │
 Group, Preset, Sequ,            tolerant, versioned)         │                 ├─ Group / Preset XML        ▼
 Macro, Effect, Timecode,                                     ▼                 ├─ Sequence XML (hard values) Import via
 Executor, World…)                               [3] Transform passes           ├─ Macro XML (Assign/Set/Cook, "bootstrap" macro
                                                   ├─ fixture-type mapping         Patch, Assign exec, Label)  or Lua plugin
                                                   ├─ attribute-name mapping    └─ Lua plugin (optional:        │
                                                   ├─ palette extraction           AddFixtures, Import, Cook)   ▼
                                                   ├─ recipe-ization                                     [5] Verification:
                                                   ├─ effects → phasers           + conversion report       Export from MA3,
                                                   └─ macro translation             (HTML/CSV)                 diff against IR
```

**Inputs [documented].** Only `Export` XML from grandMA2 onPC (or a console). The `.show.gz` is treated as opaque. The converter ships a grandMA2 macro that dumps everything with `/nc /o` into `importexport`: `Export Layer 1 Thru`, `Export FixtureType 1 Thru`, `Export Group 1 Thru`, `Export Preset 0.1 Thru 0.999` … `Export Preset 9.1 Thru 9.999` (extend for pools beyond 999 and for "All" pools), `Export Sequence 1 Thru`, `Export Effect 1 Thru`, `Export Macro 1 Thru`, `Export Timecode 1 Thru`, `Export Executor …` ([grandMA2 manual: Export keyword](https://help.malighting.com/grandMA2/en/help/key_keyword_export.html)). Whether `Export World`, `Export Layout`, `Export Page`, `Export Filter` are valid keywords is unconfirmed; use the Setup → Import/Export GUI for those if not. Also run `Export /schema` once to obtain MA.xsd for the parser's test-suite [documented option, output content unverified].

**Intermediate model [inferred].** A versioned, console-neutral schema (JSON or protobuf) with these entities: FixtureType (manufacturer, model, mode, channel map with attribute names, physical ranges, instances), Fixture (fid, cid, type ref, mode, universe.address, position, subfixtures), Group (ordered fixture refs → later grid coordinates), Preset (pool, index, name, mode, per-fixture / per-type / universal rows, fade/delay rows, embedded refs), Sequence (name, options), Cue (number, parts, trig, times, MIB, mode flags, cmd), CueValue (fixture, attribute, value or preset ref, part, fade, delay, effect ref), Effect (lines: attribute, form, rate, low/high or presets, phase, width, groups/blocks/wings), Executor assignment (page, number, target, options), Macro (lines), Timecode, World, Layout. Every entity carries `source_ref` (file, element path) so the conversion report can point back to the grandMA2 object.

**Outputs [documented pattern, inferred composition].** (a) grandMA3 library XML files per object type, dropped into `gma3_library/datapools/…` and `gma3_library/patch` / `fixturetypes`; (b) one or more **bootstrap macros** (`<Macro><MacroLine Command=… Wait=…/>`) that run `Drive`, `Import … Library … At …`, `Patch`, `Assign Sequence S At Page P.E`, `Assign Group/Preset/MAtricks At … Part P.L`, `Set … Property …`, `Label`, and finally `Cook`; (c) optionally a Lua plugin (`<Plugin><ComponentLua FileName=…/>` + `.lua`) that does the same via `Cmd()` with error checking, `AddFixtures()` for the patch, and `Import()` for bulk XML; (d) an HTML/CSV conversion report listing every object converted, approximated or skipped, with reasons. Prefer macros/commands over hand-built XML for anything whose XML structure is unverified (recipes, executors, pages, layouts, worlds, filters), and prefer XML for anything bulky and verified (sequences with hard values, presets, groups, fixture types) [inferred from the version-stability evidence].

**Version pinning [documented + inferred].** Pin each writer to a grandMA3 minor version. Emit the DataVersion that the target onPC itself writes (harvest it in Phase 0); until then use `2.3.0.0`, which is known to import into 2.5.1.0. Never emit a DataVersion newer than the target.

## B2. Recipe strategy

The goal is a show whose looks survive a change of fixture count or selection. Recipes deliver that only when the cue content is expressible as **Group × Preset (× MAtricks spread)**. The strategy therefore has five parts.

**1. Groups are the rig interface [documented concept].** Emit one grandMA3 group per grandMA2 group, with fixtures laid along X in the MA2 selection order (`<Item IDType="0" ID="…" X="i" Y="0" Z="0"/>`). Add *role groups* the converter derives itself: one group per fixture type ("All Spot 18"), one per MA2 layer, and one per distinct fixture set that appears as a unit in cue data (see palette extraction). When the user re-rigs, these groups are what they edit; everything else re-cooks from them.

**2. Presets are the look carriers, and raw cue values must become presets first [documented constraint].** Standard recipe lines take values only from presets. The converter runs a *palette extraction* pass over all cue data and existing presets:
- Keep every grandMA2 preset reference found in cue data as a reference to the corresponding grandMA3 preset (pool numbers 1–9 map 1:1; MA2 "All" presets go to MA3 All 1 (pool 10, numbering to be verified)).
- For raw values, group each cue part's values by (fixture set, feature group). If all fixtures of one type in the set share the same value vector (within a tolerance, e.g. 0.5 % for dimmer, 1° for pan/tilt), create or reuse a **Global preset** for that type in the matching pool, named deterministically ("Cue 12 Color A", or by colour name/dimmer level when recognisable). Deduplicate across the show by value hash with tolerance so that "Red" appears once.
- If values differ per fixture (typical for positions, and for hand-balanced dimmer levels), create a **Selective preset** covering exactly those fixtures, or, if the user chooses, leave the values as hard values (see 5).
- Dimmer-only data that is type-independent may become a **Universal preset** so it applies to any future fixture; beware the known universal-preset holes for slotted attributes (colour wheels, gobos), which should stay Global [community].
- MA2 Global/Universal presets translate to MA3 Global/Universal presets directly (`PresetModeInternal` or the `/Global`/`/Universal` store option); MA2 embedded presets become MA3 embedded presets by storing the parent preset "At" the child presets, or, more simply, by emitting the parent as a recipe preset whose lines reference the children [documented feature, inferred method].
- MA2 timing-only presets have no value payload; convert them to per-line Fade/Delay columns on the recipe lines that reference the feature group, or to Preset*n*Fade/Delay on the part [inferred].

**3. Cues become recipe lines plus a cook [documented syntax].** For each cue part, emit one recipe line per (group, preset) pair: `Assign Group G At Sequence S Cue C Part P.L`, `Assign Preset T.N At Sequence S Cue C Part P.L`, `Set Sequence S Cue C Part P.L Property "SelectionMode" "Strict"` for selective-origin data or `"Normal"` for type-wide data, and `"Enabled" "Yes"`. Per-fixture fade/delay spreads that were linear in MA2 become `FadeFromX`/`FadeToX`, `DelayFromX`/`DelayToX`. Cue-level timing is set on the part (`CueInFade`, `CueOutFade`, `CueInDelay`) in the sequence XML or with `Store Cue N CueFade x CueDelay y`. After all lines of a sequence are created, run `Cook Sequence S /MergeLowPriority` so that any hard values emitted alongside are preserved.

**4. Effects become phaser presets referenced by recipe lines [documented target, inferred mapping].** Each MA2 effect line is converted to a grandMA3 **phaser preset** (two or more steps) in a dedicated pool (follow MA's convention: pool 22 "Effects", or the matching feature-group pool), stored Global per fixture type where the effect used plain values and Selective where it used selective presets as low/high. The recipe line that applies it references the effect's selection group, the phaser preset, and MAtricks columns that carry MA2 Groups/Blocks/Wings (`XGroup`, `XBlock`, `XWings`) with `PhaseFromX`/`PhaseToX` for the MA2 phase range and Speed in BPM (MA2 Rate 1 = 60 BPM). Form mapping, consistent with what MA's converter and ACT describe but numerically unverified: sine → 2 steps with Accel/Decel −100 %; linear/ramp → Accel/Decel 0 %; chase / hard steps → Width 0 % (instant); stomp → single relative step to 0. Free-form user Forms, bitmap effects and lines on attributes outside the feature group cannot be mapped and are listed in the report. Because MA3 phaser distribution follows the grid, use Adaptive Measure/Width (2.4+) on phaser recipes where the MA2 effect spread its phase evenly over the selection [documented features, inferred use].

**5. Everything that cannot be a recipe stays a hard value in its own part [inferred, grounded in cook semantics].** Fixture-specific one-offs (unique positions, individually tweaked levels the user does not want as selective presets, release/off keywords, values on attributes with no preset) are written as ordinary `<Phaser><Step Absolute=…/>` values in the sequence XML. Put them in **part 0** and the recipe lines in **part 1+** (or the reverse, consistently) so that a later `Cook … /Overwrite` on the recipe part never destroys them, and so that the Track Sheet shows at a glance which data is rig-portable. Mark this choice in the report; hard values outrank recipe values on the same fixture+attribute, which is the intended behaviour for one-offs.

**Selective presets after a rig change [documented].** A selective preset only covers the fixtures it was stored for; new fixtures of the same type get nothing from it. The converter's report should list every selective preset with the fixtures it covers, and the generated show should include a "Re-rig checklist" macro that selects each affected group and recalls the preset so the programmer can update it. Where the user accepts type-wide behaviour, offer a flag that promotes a selective preset to Global when all fixtures of a type held the same value.

**Executors [documented numbering].** Map MA2 fader executor N (1–90) on fader page P to `Page P.(200+N)` and MA2 button executor 1NN to `Page P.1NN`; emit `Assign Sequence S At Page P.E`. If MA2 fader page ≠ button page (pages not linked), emit a page per MA2 fader page and append the button executors of the button page most often active with it; document the ambiguity. Executor options (priority, fader function Master/X-fade/Rate, button functions) become `Set Sequence S Property "Priority" "High"` and `Assign [Function] At Page P.E`; Special Masters become Masters. Chaser-only sequences receive `TrigType="Time"` with `TrigTime` = 60/BPM per cue, as MA's converter does [documented]. Skip X-keys 5/6/15/16, report them.

**Macros [documented limits, inferred method].** Translate line by line with a tokenizer and a rule table (`Assign … /Priority=` → `Set … Property "Priority"`; `FaderPage`/`ButtonPage` → `Page`; `Executor 1.5` → `Page 1.205`; `Store Preset 4.1`, `Label`, `Fixture … At …` pass through). Lines that cannot be translated are emitted with `Enabled="No"` and the original text in the `Note` property, so the macro imports cleanly and the user sees exactly what to fix. Expect the console to rewrite command text outside quotes on import [community].

## B4. Phases, milestones and acceptance tests

All tests use the free grandMA2 onPC 3.9.x (Windows; 4,096-parameter cap, offline) and the free grandMA3 onPC 2.5.x (Windows/macOS) ([grandMA2 onPC product page](https://www.malighting.com/product-archive/product/grandma2-onpc-grandMA2_onPC/); [grandMA3 downloads](https://www.malighting.com/downloads/products/grandma3/)). Keep a reference show in grandMA2 ("Golden Rig": 12 spots of one type, 8 washes of another, 24 dimmer channels, one multi-cell bar) and grow it per phase.

**Phase 0 — Lab and sample harvesting (1–2 weeks).**
Install both onPCs; build the Golden Rig in grandMA2 with groups, selective/global/universal presets, an embedded preset, a timing-only preset, three effects (sine, ramp, chase), a 20-cue sequence with parts, MIB, follow/time triggers, CMD, and executors on two pages; export everything with the dump macro; run "Save as grandMA3" for a reference conversion. In grandMA3 onPC, build a mini-show by hand with a recipe cue (group + global preset + MAtricks), a phaser preset, a world, a filter, a layout, and an executor assignment, then `Export` each object to obtain **real XML samples**, including the real `DataVersion`. Run `List Attribute`/Attribute Definitions export in MA3 and inspect `ChannelType@attribute` names in the MA2 fixture-type exports to start the attribute cross-reference.
*Acceptance:* a folder of MA2 exports covering every object type the converter will read; a folder of MA3 exports covering every object type it will write; a first attribute cross-reference CSV with ≥ 95 % of the Golden Rig's attributes mapped.

**Phase 1 — MA2 reader and intermediate model (2–3 weeks).**
Implement a namespace-agnostic, BOM- and stylesheet-tolerant parser for Layer, FixtureType, Group, Preset, Sequ, Macro, Effect, Timecode, Executor. Validate against MA.xsd from `Export /schema` where possible. Serialise to the IR.
*Acceptance:* round-trip test — IR → regenerated MA2 XML → `Import` into a fresh grandMA2 show reproduces the Golden Rig's groups, presets and cue values with no import errors; parser handles schema versions 3.3–3.9.60.

**Phase 2 — Patch and groups (2 weeks).**
Fixture-type matcher (manual mapping file + fuzzy suggestions + footprint check), patch XML writer, group XML writer, bootstrap macro, report.
*Acceptance:* importing the output into an empty grandMA3 show yields fixtures with the same FIDs/CIDs, addresses and positions as the MA2 patch (compare an MA3 patch export with the IR); every group selects the same fixtures in the same X order; unmatched fixture types appear in the report, none silently.

**Phase 3 — Presets (2–3 weeks).**
Preset writer for selective/global/universal; attribute and value scaling (MA2 0–100 / physical → MA3 `Absolute` / `AbsolutePhys`); embedded and timing-only handling.
*Acceptance:* for each Golden Rig preset, recalling it in MA3 produces the same physical output as in MA2 within tolerance (compare the MA3 fixture sheet physical values with the MA2 values from the export); global/universal presets apply to a newly added fixture of the same type.

**Phase 4 — Sequences as hard values (2 weeks).**
Sequence XML writer with one-step Phasers, parts, cue timing, triggers, MIB, Assert/X-Assert/Release, CMD passthrough.
*Acceptance:* `Export Sequence` from MA3 after import, normalise, and diff against the IR: cue count, part count, values and timings match; sequence plays through with Go in onPC without errors; tracking behaviour matches a tracking-sheet comparison of ten sampled cues.

**Phase 5 — Palette extraction and recipe-ization (3–4 weeks).**
Implement the clustering, preset deduplication, naming, recipe-line emission (Assign/Set macro or Lua `Cmd`), hard-value part separation, and `Cook`.
*Acceptance:* (a) the recipe-based show produces the same output per cue as the Phase-4 hard-value show (diff of MA3 exports after cook); (b) **re-rig test** — add two spots to the "All Spots" group in MA3, run the generated "Recook" macro, and verify the new spots follow every look built from Global presets, while selective-only data is listed in the re-rig checklist; (c) remove a fixture from a group and confirm its cooked data disappears after cook; (d) hard-value parts are untouched by `Cook … /Overwrite` on the recipe parts.

**Phase 6 — Effects to phasers (2–3 weeks).**
Effect → phaser-preset writer, MAtricks column emission, form calibration against the MA's own converted output and visual comparison in the MA3 3D viewer.
*Acceptance:* sine, ramp and chase effects on dimmer and pan/tilt from the Golden Rig produce visually equivalent motion at the same BPM; phase spreads, blocks and wings match; unmappable forms are reported.

**Phase 7 — Executors, pages, macros, timecode (2 weeks).**
*Acceptance:* every MA2 executor that had a sequence is on the mapped MA3 executor; chaser BPM reproduced; macros import with translatable lines enabled and others disabled with notes; timecode events trigger the right cues in MA3.

**Phase 8 — Verification tool and report (1–2 weeks).**
Export-based differ (MA3 `Export` → normalised JSON → compare to IR), HTML report with per-object status, and a "known gaps" page auto-generated from the report.

**Phase 9 — Field trial (ongoing).**
Convert three real shows of increasing complexity, compare against "Save as grandMA3" output, and gather programmer feedback on preset naming and recipe granularity.

## B5. What must be verified empirically before coding each writer

These are the research gaps; each is cheap to close with the two free onPC applications but blocks the corresponding writer until closed.

1. **Real exported grandMA3 Sequence XML containing recipe lines and cooked data** — element names (`StandardRecipe`?/`PhaserRecipe`?), how Selection/Values/MAtricks references are serialised (path, name or number), and whether cooked values are written. This decides whether recipes can be emitted as XML at all or must be created by commands.
2. **The exact `DataVersion` string that grandMA3 2.5.1.x writes**, and the behaviour on import of a DataVersion newer than the running version.
3. **Real grandMA2 Sequence export with preset references, per-attribute fade/delay and effect references** — the attribute names on `CueData`/`CuePart` for those were never observed; only raw values and `Release` are confirmed.
4. **The exact `preset_mode` strings for Selective and Global** in MA2 preset exports (only `Universal` observed), and whether a `Delays` block exists beside `Fades`.
5. **A complete MA2 → MA3 attribute-name cross-reference** (MA2 `ChannelType@attribute` such as `COLORRGB1`, `GOBO1`, `BLADE1A` to MA3 Attribute Definition `Name`, which follows GDTF conventions). No official table exists; GMA Toolbox demonstrates one can be built. Also confirm value scaling: MA2 percent-like 0–100 and physical ranges versus MA3 `Absolute` versus `AbsolutePhys`.
6. **Patch XML import behaviour**: whether a `<Patch>` library file imports into an existing show additively, how it binds `FixtureType="1 Spot 18"` to an imported type, and whether `AddFixtures` can target a stage/layer other than the current destination.
7. **MA3 Group XML grid semantics**: that `Item X=i` reproduces the intended selection order and that `AlignRangeX`/`PreserveGridPositions` defaults are acceptable.
8. **Phaser form calibration**: the Accel/Decel/Width/Transition numbers that reproduce MA2 sine, ramp, chase and other predefined forms; use MA's converted pool-22 presets as a reference.
9. **Executor/page, World, Filter, Layout, Appearance XML** — no samples exist; confirm whether macros (`Assign … At Page`, `Store World`) are the only reliable route.
10. **MA2 Export keyword coverage**: whether `Export World`, `Export Layout`, `Export Page`, `Export Filter`, `Export Executor` are valid, and the dedicated subfolder names per object type.
11. **Cue-mode semantics**: confirm MA3 property names for Assert/X-Assert/Release/MIB and whether MA2 "Release" should map to MA3 Release or to an Off command in CMD.
12. **MA3 pool numbering** for All 1–5 and the effect pool (only "pool 22 = Effects" is documented).
13. **Universal presets in recipes** for slotted attributes and the behaviour of Value Absolute on single-step lines (2.4/2.5).
14. **Cook performance** on large sequences (no benchmarks exist; one tool self-limits to 200 cue parts per cook).
15. **Lua object API** on 2.5: `Create`/`Append`/`Insert` for recipe lines is reported broken since 2.4; confirm before relying on anything other than `Cmd()`.

## B6. Known risks and limitations

- **Fidelity ceiling for positions.** Positions are inherently selective; a re-rig cannot inherit them from a Global preset. The converter can only preserve them as selective presets or hard values and give the programmer a checklist. XYZ-based MA2 programming has no faithful path at all; converted MA2 fixture types are reported to lose XYZ behaviour [community].
- **Fixture types are the weakest link.** Carrying MA2 profiles produces Source="grandMA2" types that cannot export as GDTF and misbehave in 3D; mapping to native/GDTF types changes attribute sets and physical ranges and needs human review of every type [documented + community].
- **Recipe granularity vs. programmer intent.** Palette extraction will create many presets and recipe lines; over-clustering merges looks the programmer considered distinct, under-clustering bloats pools. Tolerances must be configurable and the naming deterministic.
- **Hard values override recipes.** Any value the converter leaves hard on the same fixture+attribute as a recipe will mask the recipe after a re-rig until the user cooks with `/Merge` or `/Overwrite`; part separation reduces but does not eliminate confusion [documented].
- **Grid-dependent distributions.** Phases/widths depend on the selection grid; a rig change alters effect spreads unless Adaptive Measure/Width (2.4+) is used, which itself changes the look slightly [documented + community].
- **Semantic mismatches.** MA2 Release/Break cue modes, Assert Effects, free-form Forms, Loop/Ltime/Lcount, fader/button page splits, X-keys 5/6/15/16, remote types and layout element types have no exact MA3 counterpart; these are reported, not converted.
- **Macro translation is heuristic.** Executor addressing and option syntax differ fundamentally; MA Lighting itself declines to translate macro text [documented].
- **Schema drift.** Neither format has a published XSD; MLA ships a separate plugin per MA3 minor version and the Lua tree changed in 2.5. Every writer must be re-validated per grandMA3 minor release [documented pattern].
- **Import leniency is not a guarantee.** Older DataVersions import today; nothing promises they will tomorrow, and an unverified newer DataVersion may be refused.
- **No merge into an existing show** is attempted by MA's converter; this tool can offer it only via `Import … At` into free slots and `Clone … If …`, which needs collision checks on FIDs, pool slots and names [community].
- **Legal/compatibility.** All formats are proprietary and reverse-engineered from exports; behaviour may change without notice, and testing beyond onPC's parameter limits requires MA hardware.

## Conclusion

The research reframes the problem. The hard part of an MA2 → MA3 converter is not reading grandMA2 or writing grandMA3; both sides have stable, hand-authorable XML and the official converter already proves the mapping for patch, groups, value presets and cues. The hard part is the **semantic lift from "values in cues" to "groups × presets in recipes"**, which no tool, including MA's own, performs today ("desired by many, but does not yet exist"). That lift is a clustering and naming problem over cue data, constrained by the rule that standard recipe lines cannot hold raw values and by the fact that hard values outrank cooked ones. Designing the converter around palette extraction, Global presets per fixture type, strict part separation and an explicit `Cook` step turns the console's constraints into the mechanism that delivers rig independence.

The second implication is procedural: the single biggest unknown, how grandMA3 serialises recipe lines and which DataVersion 2.5.x writes, can be closed in an afternoon with the free onPC by exporting one hand-built recipe cue. Until that export exists, the only safe way to create recipes is the command path (`Assign … At … Part P.L`, `Set … Property …`, `Cook`), which is exactly how the one open-source project that does this today works. Build the command path first, treat XML emission of recipes as an optimisation to be unlocked by a sample file, and keep the official "Save as grandMA3" output as the regression baseline against which every phase is measured.
