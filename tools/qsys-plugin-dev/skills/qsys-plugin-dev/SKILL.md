# Q-SYS plugin development

A Q-SYS plugin is one Lua file with the `.qplug` extension. Q-SYS Designer runs
the top of the file at design time to learn what the block looks like (its
properties, pins, controls, layout and the DSP components inside it), and the
Core runs the same file again at runtime with the global `Controls` present.
Everything in this skill follows from that split, so read the file you are
editing with that split in mind: design-time code must be deterministic and
side-effect free, runtime code lives under `if Controls then ... end`.

Author every plugin, README and code file for this user as
"Nikita Visual Arts – nikitavisual.art": a header comment at the top of the
file, the `Author` field of `PluginInfo`, and the brand name and site in the
plugin's header area. Delivered files carry no tool attribution of any kind:
no generator notes, no assistant names, no "generated by" comments.

## Workflow

1. **Pin down the block.** Before writing any Lua, decide the inputs and
   outputs (audio pins), the user-facing properties that change the block's
   shape (channel counts, modes), the controls (what the operator turns or
   presses), and which embedded Q-SYS components do the actual DSP. Write
   this down as a short list in your reply when the request is vague, and
   proceed with the most sensible reading rather than stopping.
2. **Start from the template.** Copy `assets/plugin-template.qplug` (all
   paths in this skill are relative to the skill folder that holds this
   SKILL.md) next to the other plugins (this repo keeps them in `plugins/`)
   and rename it. It is a complete, loadable plugin: a brand header with the
   logo already embedded, one property, a gain fader, mute button and meter
   per channel, a Status LED, an n x n mixer wired in to out, and a runtime
   block. Replace parts instead of starting from an empty file, since the
   parts that are easy to get wrong (page handling, `Count = 1`, status
   values, default values) are already right in it. Give it a new GUID at
   once: `python3 -c "import uuid; print(uuid.uuid4())"`. When the request
   names a count ("a 4-channel block, 1 to 8"), the named count is the
   property default and the range is its Min and Max.
3. **Write the design-time tables in order**: `PluginInfo`, `GetProperties`,
   `RectifyProperties`, `GetPages`, `GetControls`, `GetControlLayout`,
   `GetPins`, `GetComponents`, `GetWiring`. Field names and allowed values
   are in `references/design-time-api.md`. Read that file the first time you
   touch any of these functions in a session; it is short.
4. **Write the runtime block.** Control access, embedded component access,
   timers and the Status indicator are in `references/runtime-api.md`.
5. **Check before you hand over.** Run the checker on the file:

   ```bash
   python3 <skill folder>/scripts/check_plugin.py plugins/MyPlugin.qplug
   ```

   It checks Lua syntax (with `luac`, or the `lupa` Python package: run
   `pip install lupa` once if neither is present), and with `lupa` it also
   executes the design-time functions for the default properties and for
   each integer property's Min and Max, cross-checking layout keys against
   controls and wiring endpoints against pins and components. It always
   checks the things Designer does not warn about: a missing or malformed
   `PluginInfo`, controls declared with `Value` instead of `DefaultValue`,
   unknown `Style`, `Font` and `ControlUnit` values, and a missing brand
   header. Fix every error; read each warning and decide.
6. **Report honestly.** Nothing here runs Q-SYS Designer or a Core. Say in
   the hand-over that the plugin was syntax-checked and statically checked
   but not loaded in Designer, and list the names (component `Type` strings,
   control names inside components) that are the most likely to need a fix
   on real hardware.

## The shape of a plugin

```lua
-- Nikita Visual Arts – nikitavisual.art
PluginInfo = { Name = "Nikita Visual Arts~My Block", Version = "1.0.0", BuildVersion = "1.0.0.0",
  Id = "<new GUID>", Author = "Nikita Visual Arts – nikitavisual.art", Description = "...", ShowDebug = false }

function GetColor(props) return { 23, 21, 28 } end        -- block colour in the schematic
function GetPrettyName(props) return "My Block" end        -- block title in the schematic
function GetProperties() return { {...}, {...} } end       -- Properties pane
function RectifyProperties(props) return props end         -- hide or clamp properties
function GetPages(props) return { { name = "Main" } } end  -- optional UI pages
function GetControls(props) return ctls end                -- knobs, buttons, texts, indicators
function GetControlLayout(props) return layout, graphics end
function GetPins(props) return pins end                    -- audio or serial pins on the block
function GetComponents(props) return comps end             -- embedded Q-SYS components
function GetWiring(props) return wiring end                -- connections between pins and components

if Controls then
  -- runtime: read Properties, drive component controls, react to Controls
end
```

`PluginInfo.Name` with a tilde ("Vendor~Block") files the plugin under a
folder in the Designer plugin list. Generate a fresh GUID for `Id` for every
new plugin, and never reuse one across plugins, since Designer identifies the
plugin by it. Bump `Version` on every released change.

## Things that bite

These are the mistakes that cost the most time in practice. Each one compiles
fine and only shows up as wrong behaviour in Designer or on a Core.

- **Control defaults use `DefaultValue`, not `Value`.** A `Value` key on a
  control table is ignored, and a Knob without `DefaultValue` starts at its
  `Min`. The symptom is every fader at the floor, every pan hard left.
- **`Count = 1` gives a single object, not a one-element array.** At runtime
  `Controls.Gain` is the control itself when `Count` is 1 and an array when
  it is larger. Normalise with a helper so the rest of the code can index:
  `local function arr(c, n) return n == 1 and { c } or c end`.
- **Layout keys follow the same rule.** The layout key for a control with
  `Count = 1` is its `Name`; with a larger count it is `"Name 1"`,
  `"Name 2"`, and so on. The template's `idx()` helper does this.
- **Pages.** When `GetPages` returns more than one page, Designer calls
  `GetControlLayout` once per page with `props["page_index"].Value` set, so
  branch on that and only lay out the controls that belong to the page.
  Controls not placed on any page are still created, just invisible.
- **Embedded components become globals named after their `Name`**, so names
  must be valid without spaces, and an unknown `Type` is dropped silently.
  Probe for the global at runtime (`_G["reverb_fx"] ~= nil`) and show the
  result in a Status indicator instead of assuming the engine exists.
- **Design-time functions must not depend on runtime state.** They are called
  repeatedly while the user edits properties; keep them pure and fast, and
  never call `print` or `Timer` from them.
- **Dynamic sizes come from properties.** A plugin's channel count, page set
  and layout are all recomputed from `props` on every property change, so
  derive every count from `props["..."].Value` and never cache it in a global
  at design time.

## Layout and brand

Lay the control panel out on an 8 px grid with a 16 px outer margin, a header
band of about 48 px, and groups in `GroupBox` graphics. Put the brand in the
header: the name "Nikita Visual Arts" as a bold label, the site
"nikitavisual.art" as a smaller muted label, the block title right-aligned,
and the logo as an `Image` graphic whose `Image` field is the base64 of
`assets/brand/logo-icon.png` (the project's `assets/brand/` folder, never a
dot-folder path). The template already embeds that file as
`NikitaAssets.Icon`; only regenerate it for a different image:

```bash
python3 <skill folder>/scripts/embed_image.py assets/brand/logo-icon.png --name Icon
```

Clamp the panel width to a minimum (the template uses 320 px) so a one-
channel block still has room for the header. When `Font` is omitted,
Designer uses its default font, which is assumed to be Roboto; name the font
explicitly whenever a `FontStyle` other than Regular or Bold is wanted.

Keep colours in one table at the top of the file so the whole panel can be
restyled in one place; the template ships the brand palette. Fonts, styles
and every enumerated value are listed in `references/ui-style-reference.md`;
only use font names and `FontStyle` values from that list, because an
unsupported combination falls back silently to a default font.

## Installing and testing

Copy the `.qplug` to the Designer plugin folder and restart Designer:

```
%USERPROFILE%\Documents\QSC\Q-Sys Designer\Plugins
```

Then drag the block from the plugin list, set the properties and press F5 to
emulate. Tick `ShowDebug` in `PluginInfo` or add a Debug property and `print`
from the runtime block; the output shows in the Designer debug window. For
plugins split across several Lua files, the Q-SYS Plugin Compiler for VS
Code assembles them into one `.qplug`. The "Better Lua for Q-SYS Plugins" VS
Code extension (`integratorblocks.qsys-intellisense`) gives hover
documentation and completions for the same API this skill describes.

The runtime half of a plugin can be exercised without reinstalling: paste it
into a Text Controller in a test design and push edits over the network with
`scripts/qrc_deploy.py` (list, get and push a script component's code on a
Core or on Designer emulation at 127.0.0.1). `references/deploy-and-test.md`
has the protocol facts and the exact commands. Only do this when the user
gives you a reachable Core address.

## Reference files

- `references/design-time-api.md`: every table and field for PluginInfo,
  properties, controls, layout, graphics, pages, pins, components and wiring.
- `references/runtime-api.md`: `Controls`, `Properties`, embedded component
  controls, `Timer`, Status values, and the runtime skeleton.
- `references/ui-style-reference.md`: fonts and font styles, control styles,
  colour format, enumerations.
- `references/deploy-and-test.md`: installing plugins, pushing scripts over
  QRC, what to report after testing.
- `assets/plugin-template.qplug`: the starting point for a new plugin.
- `scripts/check_plugin.py`: static checker and design-time sandbox run;
  `scripts/embed_image.py`: PNG to Lua base64 string;
  `scripts/qrc_deploy.py`: list, get and push script components on a Core.
